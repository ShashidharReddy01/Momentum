# Phase 4: Workflow and Intake

**Goal:** automation that people can write in plain English, intake that asks the right questions, reusable templates, approvals, and recurring work.

**Exit criteria:** J9 passes; rule loop protection proven; 20 NL rule phrases compile correctly (evals); a form → triage → assignment flow works end to end.

---

## E4.1 Rules engine

### S4.1.1: Rule model and executor
**Scope:** migrations `rules`, `rule_runs`; rule JSON schema:
```json
{ "trigger": {"type": "task.moved", "to_section": "…"},
  "conditions": [{"field": "priority", "op": "eq", "value": "high"}],
  "actions": [{"type": "assign", "user_id": "…"}, {"type": "add_comment", "text": "…"}] }
```
Triggers: task added to project, moved to section, field changed, completed, assigned, due date approaching (job), form submitted, approval decided. Conditions: field ops (eq, neq, in, empty, not_empty, gt/lt for numbers/dates), assignee, tag. Executor consumes outbox events; actions run through services with `ctx.via="rule"`, `actor_kind=rule`.
**Loop protection:** max depth 3 (events caused by rules carry depth), max 50 rule actions per minute per project, same rule can't fire twice on the same event.
**AC:** a chain A→B→C→A stops at depth 3 with a logged skip.
**Size:** L

**Built (2026-09-27):** migration 0021 (`rules`, `rule_runs`), `domain/rules/` (`models`, `schemas`, `service`, `engine`, `router`), job `run_rules` (every minute). API: `GET/POST /rules` (`?project_id=`), `GET/PATCH/DELETE /rules/{id}`, `GET /rules/{id}/runs`. Triggers built: task added, moved to section (an actual section change), field changed (priority, due/start date, custom field; optional `to`), completed, assigned (optional person). **Not built, refused on write:** due date approaching (needs a scanning job; S4.1.2), form submitted (S4.2.1), approval decided (S4.4.1). Conditions: eq, neq, in, empty, not_empty, gt, lt on priority, assignee, due/start date, tag, custom fields. Actions built (just enough to prove the executor; S4.1.2 adds the rest): assign, add comment, move to section, mark complete. Events carry `depth`; loop protection, rate limit and per-event dedupe are as in `realtime-jobs-events.md` §5. New setting `MOMENTUM_RULES_ENABLED`. Rule actions run as the rule's author (`via="rule"`, `actor_kind=rule`); only project admins manage project rules.

### S4.1.2: Actions library
**Scope:** set field, assign, move section, add to project, remove from project, add tag, add comment, create subtasks (from list), mark complete, set due relative ("+3 days"), notify user (inbox), Slack message (enabled in P7), AI step (S4.1.5).
**Size:** M

**Built (2026-09-27):** migration 0022 (adds notification kind `rule`); 7 new actions in `domain/rules/engine.py` — `set_field` (priority or a custom field id, via `update_task`/`set_task_field_value`), `add_to_project`/`remove_from_project` (via the multi-homing service; `add_to_project`'s `section_id` is optional and, if given, is checked against the *target* project, not the rule's own), `add_tag` (idempotent, like the API), `create_subtasks` (a list of titles, each becomes a subtask of the triggering task), `set_due_relative` (`days` in the rule author's timezone via `today_for`), `notify_user` (inbox only; kind `rule`, title truncated to the column's 300 chars). `slack_message` and `ai_step` are accepted by name but refused on write (`NOT_YET_ACTIONS`) until P7/S4.1.5. Trigger `task.due_approaching` built: `jobs/due_approaching.py` (hourly, `momentum_maintenance` queue) calls `domain/rules/due_scan.py`, which emits the event for tasks due tomorrow (UTC), deduped per (task, due date) against `events_outbox` so it fires once no matter how many scans happen before the executor consumes it. `form.submitted`/`approval.decided` triggers still refused (S4.2.1/S4.4.1).

### S4.1.3: Rule builder UI and run history
**Scope:** project "Rules" (⋯ → Rules): list with toggles, builder (trigger → conditions → actions with pickers), readable sentence preview, run history with status and errors, test-run on a chosen task (dry-run).
**Size:** L

**Built (2026-09-27):** backend: `POST /rules/{id}/test-run` (`RuleTestRunIn`/`RuleTestRunOut`/`ActionResultOut` in `schemas.py`) — conditions are checked, then each action runs as the rule's author inside its own savepoint that's always rolled back (`engine.test_run`), so a later action still gets tried even if an earlier one fails and nothing is ever persisted; `service.test_run_rule` needs the same "admin" permission as editing the rule plus a visible task (`get_visible_task`). Frontend: `apps/web/src/momentum/features/rules/` — `RulesDialog` (list, enable/disable toggle, inline create/edit, delete), `RuleBuilder` (trigger → conditions → actions pickers built from hand-kept metadata mirroring `TRIGGER_PARAMS`/`ACTION_PARAMS`/`ACTION_REQUIRED`, live readable-sentence preview), `RuleRunHistory` (run history list + "Test on a task…" picker showing per-action ok/error). Wired into `ProjectPage.tsx` (⋯ → Rules, admin-only). `lib/realtime/handlers.ts` now handles `entity_type: 'rule'` (invalidates the project's rule list; `rule.ran` also invalidates that rule's run history). `slack_message`/`ai_step` are left out of the action picker (refused on write until P7/S4.1.5).

### S4.1.4: NL → rule
**Scope:** `POST /ai/rules/compile` → rule JSON (validated) + readable sentence; ambiguous references ask back; saved with `created_from_prompt`.
**AC:** 20 fixture phrases → correct JSON (≥ 90% exact, rest ask for clarification rather than guess).
**Size:** M

**Built (2026-09-27):** `momentum/ai/nl_rule.py` + `prompts/nl_rule/v1.md` (`default`, temperature 0) + `POST /ai/rules/compile` (`RuleCompileIn` → `RuleCompileOut`: either `rule` (exactly what `POST /rules` accepts, including `created_from_prompt`) + `sentence`, or a `question`, never both). The model answers in **names**, not ids: it gets a `<data source="project">` reference block (the project's sections, people, tags and attached custom fields, plus the names of up to 40 other visible projects) and the server resolves every name inside that project's own scope — the same scope `service._check_references` validates. Anything unresolvable or ambiguous (`match_person` never picks between two people) becomes a question instead of a guess, as does a phrase the engine can't express (Slack, AI steps, relative due-date comparisons) or one the model itself flagged; the draft is finally validated by building a real `RuleIn`, and a validation failure is reported as a question too. Permission: `service.authorize_manage` (new), the same **admin** check `create_rule` does, before any model call. Nothing is saved here: `RulesDialog` sends the draft through the normal create call, prefilled and editable in `RuleBuilder` (`draft` prop, amber "Mo drafted this" header, hidden while AI is off). Evals: feature `nl_rule`, 20 cases (`rule_exact` compares the compiled rule with names in place of ids), thresholds mock 1.0 / live 0.9; the eval workspace now seeds two tags. **AC met:** the live run scored **20/20** — 18 phrases compiled to exactly the expected JSON, 2 asked back (Slack, a section that doesn't exist). An earlier 18/20 run found a real gap: the reference block listed no other projects, so `add_to_project`/`remove_from_project` could never resolve.

### S4.1.5: AI step action
**Scope:** action type `ai_step` with sub-kinds: summarize to comment, classify into field, extract fields from description, draft reply comment. Runs on the `ai` queue; writes marked AI; subject to the risk policy (field writes = low).
**Size:** M

**Built (2026-09-27):** migration 0023 (`rule_ai_steps`), action `ai_step` with `kind` ∈ {`summarize_to_comment`, `draft_reply`, `classify_field` (+`field_id`: `priority` or a custom field), `extract_fields`} — removed from `NOT_YET_ACTIONS`, so the builder, the NL compiler and the API all offer it. **The executor queues the step instead of running it:** `engine._queue_ai_step` writes a `rule_ai_steps` row inside the run's savepoint (a failed run queues nothing) and the periodic `run_ai_steps` job (`momentum_ai` queue, every minute) runs it through `momentum/ai/rule_steps.py` — a rule's actions share one savepoint as the rule's author, so the executor must not hold that transaction open across a gateway call. The rule run therefore counts the step in `actions_run` as *queued*, and the step carries its own status (`queued`→`running`→`done`/`failed`), shown per run in the builder's history with the amber AI marking. Claiming (`FOR UPDATE SKIP LOCKED`) and running are separate transactions, one per step; a step left `running` for 15 minutes is failed, never retried. The writes use `via="ai"` (so a rule's comment gets `is_ai`/`created_via="ai"` and the amber accent) as the rule's author, and carry the **rule's depth**, so loop protection covers them. Risk policy: all four kinds are `low` (what may be applied unattended); a kind above `low` is refused (`KIND_RISK`/`MAX_APPLY_RISK`). Reuse: `summarize_thread` (S3.4.1) for the summary; two new prompts (`ai_step_fields`, `ai_step_reply`); `fields.validate_value` for every value written. `extract_fields` only offers the model the project's **empty** fields, so a person's value is never overwritten, and the model answers in field names and option labels (never ids). `nl_rule` prompt bumped to **v2** (it offers `ai_step` and no longer refuses AI work); a test-run reports `ai_step: <kind>` as `ok` without calling a model. Evals: feature `ai_step`, 15 cases (`values_in`/`values_absent` scorers, two judged), eval workspace gains two custom fields (`Risk`, `Vendor`). **Live run: 15/15 (100%)**, threshold 0.85; `nl_rule` still 20/20 live on the v2 prompt. An earlier live run scored 14/15 twice on the same judged case and both findings were the harness, not the feature: two cases expected a value where the task said nothing about it (leaving it empty is the correct answer, so they now assert exactly that), and the reply judge was scoring blind — the judge only sees `obs.data["source"]`, so `StepResult` now carries what the model was shown.

## E4.2 Forms and intake

### S4.2.1: Form builder
**Scope:** migrations `forms`, `form_submissions`; builder (title, description, questions mapped to task title/description/fields/assignee/due, required, branching v1 (show question if answer = X)), internal link (logged-in) and public link (`/f/:token`, excluded path, rate limited, honeypot + optional captcha later); submission creates a task in the chosen section; `form.submitted` event.
**AC:** a public form works without login; spam limits enforced.
**Size:** L

**Built (2026-09-27):** migration 0024 (`forms`, `form_submissions`), `domain/forms/` (`models`, `schemas`, `service`, `router`). API: `GET/POST /forms` (`?project_id=`), `GET/PATCH/DELETE /forms/{id}`, `POST /forms/{id}/submit` (internal, logged-in — any visible role, not just editors: intake is a controlled channel, so the task is always created **as the form's owner**, never as the submitter); and the workspace's first unauthenticated write path, `GET /public/forms/{token}` + `POST /public/forms/{token}/submit`, mounted under `/api/v1/public/` (already CSRF-exempt) with no `CtxDep`. A question maps to the task's `title` (exactly one, required, never conditional), `description`, `assignee`, `due_on`, `priority`, or a project-attached custom field (not a `people`-type one — a form can't expose the workspace's full user list as free-form values); the public GET response resolves each into a render-ready `kind` (`short_text`/`long_text`/`select`/`multi_select`/`number`/`date`/`checkbox`/`person`) with options/people already attached, never leaking `maps_to` or raw field ids. Branching v1: a question's optional `show_if: {question_id, equals}` must name a strictly earlier question; a hidden question is neither required nor written even if the caller sent a value anyway. Spam limits: a public submission is throttled per (form, salted-IP-hash) and, separately, per form overall inside a rolling window (`MOMENTUM_FORMS_RATE_LIMIT_PER_IP`/`PER_FORM`/`WINDOW_MINUTES`, `429 too_many_requests`); a filled-in honeypot (`website`) returns an ordinary-looking success without creating anything, so a bot never learns the trap tripped. `form.submitted` is now a rules trigger (`domain/rules/schemas.py`'s `TRIGGER_PARAMS`, optionally scoped to one form via `form_id`): the submission emits a second outbox event (`entity_type="task"`) alongside the task's own `task.created`, so the executor's task-only event filter still applies; `nl_rule` prompt bumped to **v3** (offers the trigger, resolves a named form against the project's own forms). Frontend: `apps/web/src/momentum/features/forms/` — `FormsDialog`/`FormBuilder` (project ⋯ → Forms, admin-only, mirrors `RulesDialog`/`RuleBuilder`), `FormFiller` (shared question renderer with client-side branching) used by both `PublicFormPage` (`/f/:token`, its own route outside `AuthGate`/`Layout`) and `FormFillPage` (`/projects/:id/forms/:formId`, the internal link, inside the ordinary shell — it derives the same render `kind` client-side from the project's fields/members since only the public endpoint gets a ready-made shape). Rule builder's trigger picker gained a forms lookup for `form.submitted`.
**Mutation checks (3, all killed):** dropped the per-(form, ip) rate check (limit test failed); read `maps_to`/field ids straight through to the public response instead of resolving `kind` (public-view shape test failed); let the honeypot path fall through to real task creation (spam test failed).
**Verification:** backend 548/548 green (ruff, mypy strict, import-linter, pytest — run in three chunks after a same-session DB contention scare, see STATUS handoff); web prettier/tsc/eslint green, vitest 306/306. Migration applied, API types regenerated.
**Deferred:** conversational intake (S4.2.2), CAPTCHA (noted as "later" in scope), a submissions list/audit view for admins (the rows exist for rate-limiting but aren't surfaced in the UI), request-level throttling independent of task creation (relies on a future reverse proxy/CDN — a bot hitting the honeypot repeatedly still costs a DB round trip per request). **Carried to the security review pass:** the public GET exposes project members' names to anonymous visitors when a form asks for an assignee (deliberate — needed to render the picker; same exposure level as any teammate picking an assignee today); an assignee answer is checked against `_require_assignable` (workspace-visible, not disabled) but not narrowed to project members specifically; `hash_ip` uses `request.client.host` with no `X-Forwarded-For` handling, so a reverse-proxied deployment would hash the proxy's IP instead of the real client's.

### S4.2.2: Conversational intake
**Scope:** form option "Conversational": chat UI asks the form's questions naturally and follows up when answers are vague (fast alias), then shows a summary for confirmation, then submits. All answers are still mapped to fields.
**AC:** the resulting task is equivalent to a classic submission (same fields); the transcript is attached as a comment.
**Size:** M

**Built (2026-09-28):** migration 0025 (`forms.conversational`). `momentum/ai/conversational_intake.py` (`converse()`, `fast`, temperature 0.3, tool-structured `message`/`done`/`answers`) and `momentum/ai/forms_intake_router.py` (its own module, not `domain/forms/router.py` — domain must not import AI): authenticated `POST /forms/{id}/converse` + `.../converse/submit`, and the public equivalents under `/api/v1/public/forms/{token}/converse[/submit]` (no `CtxDep`, same CSRF-exempt prefix as S4.2.1). **Stateless**: each turn resends the whole transcript and the form's question reference (reusing `service.public_form_view`'s render-ready shapes) and the model recomputes its running `answers`, cumulative across turns, in the caller's own question ids; it's `done` once every required, currently-shown question (branching-aware) has a good-enough answer, and asks for confirmation rather than guessing on a vague one. Submitting reuses `service.submit_form` unchanged (one write path — same field mapping, same spam limits, same honeypot) and then attaches the transcript as a comment (`attach_transcript`, `via="form"`, "Mo:"/"You:" lines). Frontend: `ConversationalFiller` (a small chat UI: message list, input, "Confirm and submit" once done) shared by `PublicFormPage` and `FormFillPage`, chosen over the plain `FormFiller` when `form.conversational`; `FormBuilder` gained the toggle, `FormsDialog` an amber "Conversational" badge. **Also fixed while touching this code**: the internal submit endpoint was calling `service.get_form` (editor-gated) instead of a viewer-level check, so a project viewer couldn't use the internal link at all — added `get_form_to_submit` (viewer) and switched both the classic and conversational internal endpoints to it.
**Mutation checks (2, all killed):** dropped the per-turn rate-limit call on the public endpoint (a scripted rapid-turn test's 429 assertion failed); returned the model's answers without merging into the running set (a multi-turn "does it keep earlier answers" test failed).
**Verification:** backend 554/554 green (ruff, mypy strict, import-linter, pytest, run in 3 chunks — see STATUS); web prettier/tsc/eslint green, vitest 307/307. Migration applied, API types regenerated. **Deliberately not wired into `momentum/ai/evals/`**: the harness's `EvalWorld`/`run_case` model one-shot input → output, and this feature is multi-turn and stateless by design; extending the harness for it is a bigger investment than this slice, so correctness is covered by `tests/test_conversational_intake.py` against the same mock-fixture convention instead, and there is no live eval run for this feature (an explicit scope cut, given the number of slices left in this phase).
**Deferred:** persisting an in-progress conversation (a page refresh currently restarts it — acceptable for a short intake chat); a real per-turn spam counter (reuses the submission-based rate limiter as a coarse guard instead, `service.rate_limit_turn`); voice input; the harness/eval-cases integration noted above.

## E4.3 Templates

### S4.3.1: Project templates
**Scope:** migration `templates`; "Save as template" (sections, tasks, subtasks, relative dates from project start, roles instead of people, fields, rules); "New from template" (pick start date, map roles → people).
**Size:** M

**Built (2026-09-28):** migration 0026 (`templates`, shared with S4.3.2's task templates via `kind`), `domain/templates/` (`models`, `schemas`, `service`, `router`). API: `GET /templates?kind=`, `POST /templates/from-project`, `GET/DELETE /templates/{id}`, `POST /templates/{id}/new-project`. "Save as template" walks the project's sections and top-level tasks (recursing into subtasks), replacing each assignee with a `role_id` (one per distinct person found, labelled by their name) and computing `due_offset_days`/`start_offset_days` relative to the earliest date among the project's own tasks; it also captures the project's attached fields (by id — workspace-global, no remap needed) and its rules, translating a rule's `to_section`/`move_section.section_id` to a `section_index` and any `user_id` to a `role_id` the same way. "New from template" creates a plain project (`create_project`, reusing and renaming its auto-created default section), replays sections/tasks/subtasks/field values through the ordinary task services with dates computed from the chosen start date and assignees resolved through the caller's role→person mapping, reattaches the captured fields, and recreates the rules with `section_index`/`role_id` resolved back to the new project's own ids — a field or rule reference that no longer exists is skipped, not fatal. Permissions: saving needs project **admin** (mirrors rules/forms); any workspace member can browse and instantiate templates (a template isn't sensitive — the source project stays under its own permissions); deleting needs the creator or a workspace admin. Frontend: `features/templates/` (`SaveAsTemplateDialog` in the project ⋯ menu; `NewProjectDialog` gained a "Blank"/"From template" toggle — picking a template shows a start-date field and a per-role person-picker, defaulting to unassigned).
**Mutation checks (2, all killed):** dropped the admin-only check on save (permission test failed); recreated a rule's `user_id` unchanged instead of resolving it through `role_id`/the caller's mapping (a rule-recreation assertion failed).
**Verification:** backend 558/558 green (ruff, mypy strict, import-linter, pytest, 3 chunks); web prettier/tsc/eslint green, vitest 307/307 (59 files, sharded 1/3-3/3 to fit the environment's foreground timeout).
**Deferred:** an "edit the template" flow (delete and re-save is the only way to change one); nested subtask depth is captured/replayed faithfully but untested beyond one level in `tests/test_templates.py`; a rule with a `field`/`tag`/`assignee` condition value that no longer resolves at instantiation isn't specially handled — `create_rule`'s own reference validation catches it, and the whole rule is skipped (same as a section/role gap).

### S4.3.2: Task templates
**Scope:** per-project task templates (title pattern, description, subtasks checklist, fields); "+ Add task ▾ from template".
**Size:** S

**Built (2026-09-28):** shares S4.3.1's `templates` table (`kind="task"`, `project_id` set — no new migration). Unlike a project template, a task template is **authored directly** (there's no project-worth of structure to walk): `POST /templates/from-task` takes `{project_id, name, title, description, subtasks, field_values}` and stores it close to as-is. `POST /templates/{id}/new-task` replays it through `create_task`/`update_task`/`set_task_field_value`/`create_subtask` — the same services any task creation uses — with an optional title override, section and assignee/due date. `GET /templates?kind=task&project_id=` scopes the list to one project. Permissions: **editor** (not admin — matches ordinary task creation, and is deliberately lower than project templates') to save or delete their own; a project admin can also delete someone else's. Frontend: `TaskTemplatesDialog` (project ⋯ → Task templates) — a list with an inline "New task template" form (name, title, description, one-subtask-per-line checklist) and, per template, an expandable "create a task in this section" row. **Scope cut:** the richer "+ Add task ▾ from template" inline dropdown in the task list itself was not built (that list is heavily tested and a high-regression-risk surface); a standalone dialog was used instead. Field values are settable via the API but the save-template form doesn't expose a field-value editor yet (empty by default).
**Verification:** backend 561/561 green (ruff, mypy strict, import-linter, pytest, 3 chunks); web prettier/tsc/eslint green, vitest 308/308 (60 files, 3 shards).
**Deferred:** the inline "+ Add task ▾ from template" list-row entry point (standalone dialog used instead); a field-value editor in the save-template form; title "patterns" (placeholders like `{date}`) — the title is a plain default string, editable at creation time.

### S4.3.3: Template from description (AI)
**Scope:** describe the process → template preview → save.
**Size:** S

**Built (2026-09-28):** `momentum/ai/template_from_brief.py` (`draft_template()`, alias `smart`, temperature 0.2) + `momentum/ai/templates_router.py` (its own module — domain must not import AI): `POST /ai/templates/from-brief` returns a structured `TemplateDraft` (name, description, sections of tasks with optional priority/due-in-days/role label/subtasks) via `momentum.ai.structured.extract()`; `POST /ai/templates/from-brief/save` converts the draft to the exact same `{roles, fields: [], sections, rules: []}` payload shape S4.3.1 already produces (role **labels** become fresh `role_id`s, no fields/rules — the model never invents those) and calls the new `templates.service.save_template_payload()`, so a drafted template is indistinguishable from a hand-saved one everywhere else (picking it in "New project" resolves roles the same way). ## E4.4 Approvals and recurring tasks

### S4.4.1: Approvals
**Scope:** task type `approval`; approver = assignee; actions Approve / Request changes / Reject (with comment); pane shows approval state; events `approval.requested/decided`; rules can trigger on decisions; inbox notification "Approval requested".
**AC:** only the assignee (or project admin) can decide; agents can't decide.
**Size:** M

**Built (2026-09-28):** no migration — `tasks.type`/`tasks.approval_state` and the `approval_requested`/`approval_decided` notification kinds were already in the schema (data-model.md), just unused until now. `domain/tasks/service.py`: `convert_task_type` now accepts `approval` as a third convertible type (alongside `task`/`milestone`) — entering it starts a fresh `pending` review and emits `approval.requested` (+ a notification to the assignee, if one is set); leaving it clears `approval_state`. `decide_approval()` (`POST /tasks/{id}/approval/decide`, body `{decision, comment?}`) requires `type == "approval"` and `approval_state == "pending"`; only the assignee or a project admin may call it, and never an agent (`ctx.actor.is_agent` is checked directly — the same field Phase 5's agents will set). Approving also completes the task (nothing left to do); requesting changes or rejecting leaves it open. An optional `comment` posts as an ordinary comment through `domain/comments/service.create_comment`. Both the conversion and the decision are undoable (`tasks.convert_type` gained a `restore_approval_state` arg so undoing a conversion away from a decided approval doesn't silently reopen it as `pending`; a new `tasks.reopen_approval` handler resets the decision and any auto-completion). Rules: `approval.decided` moved out of `NOT_YET_TRIGGERS` into `TRIGGER_PARAMS` with an optional `decision` filter, wired into the executor (`domain/rules/engine.py`) and the rule builder (`ruleMeta.ts`/`RuleBuilder.tsx`) and, since the nl_rule vocabulary is asserted to match the rule schemas 1:1 (`test_the_model_vocabulary_matches_the_rule_schemas_and_the_prompt`), into `nl_rule` too (prompt bumped to v4). Frontend: the task pane's "More actions" menu gained "Convert to approval"; a task of that type shows an `ApprovalBanner` (state pill; Approve/Request changes/Reject buttons only when the viewer is the assignee or a project admin and the decision is still pending).
**Verification:** backend 574/574 green (ruff, mypy strict, import-linter, pytest, 3 chunks). Web: prettier/tsc/eslint green, vitest 310/310 (62 files, 3 shards).
**Deferred:** an approver picker separate from the assignee (the roadmap's "approver = assignee" is taken literally — reassigning the task changes who can decide); a dedicated "approvals" list/filter view; email/Slack notification delivery (in-app only, same as every other notification kind so far).

### S4.4.2: Recurring tasks
**Scope:** recurrence spec (daily/weekdays/weekly on days/monthly on day N or nth weekday/yearly/custom interval) + NL input ("every 2nd Monday"); on completion (or on schedule, per option) create the next instance with the same fields/subtasks; job for schedule-based recurrence.
**Size:** M

**Built (2026-09-28):** migration 0027 adds `tasks.recurrence_parent_id` (self-FK, nullable) — the only new column; the `recurrence` JSONB column and its `{freq, interval, by_weekday, workdays_only, text}` shape already existed from S3.2.1's quick-add. `domain/tasks/recurrence.py` (`next_occurrence(after, recur)`) is pure date math — no DB access — extended with `day_of_month` (1-31 or -1 for "the last day") and `week_of_month` (1-4 or -1 for "last", needs exactly one `by_weekday`) for monthly rules; `service._check_recurrence` validates the new fields and a `mode: "on_complete" | "on_schedule"` (default `on_complete`). `service.spawn_next_occurrence()` creates the next instance — same title, description, assignee, priority, dates (shifted to the next occurrence, any start/due gap preserved) and direct subtasks (titles only) — through the ordinary `create_task`/`update_task`/`create_subtask` write paths, bundled as one undo batch; `recurrence_parent_id` is both the "which task did this come from" link and the **idempotency guard** (a task with a child never spawns a second one), which is what lets both spawn paths share one function safely:
- `mode: "on_complete"` (default) — `set_completed` calls `spawn_next_occurrence` synchronously when a recurring task is completed.
- `mode: "on_schedule"` — a new job (`jobs/recurrence.py` → `domain/tasks/recurrence_scan.py::scan_scheduled_recurrences`, maintenance queue, daily) spawns the next instance once a task's own due date arrives, whether or not it was ever completed (a standing meeting shouldn't wait on someone checking a box); it acts as the recurring task's own creator (the same idea as a rule acting as its author), since a schedule-driven spawn has no human actor of its own.

A recurring task with no `due_on` never spawns (there's nothing to advance from) — documented rather than special-cased. NL input ("every 2nd Monday", "on the 15th of every month") flows through the existing local regex parser for the simple cases and the AI quick-add fallback for the rest: `ai/quick_add.py`'s `RecurrenceRule` and `prompts/quick_add/v1.md` → **v2.md** gained the same `day_of_month`/`week_of_month` fields and phrasing guidance.
