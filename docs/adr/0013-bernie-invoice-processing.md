# ADR-0013: Bernie, the invoice agent

- **Status:** Accepted
- **Date:** 2026-10-08
- **Deciders:** product owner, AI (drafted)

## Context
The product owner has a standalone invoice-extraction pipeline (the COAP hackathon notebook, copied for reading only at `docs/reference/coap-invoice-pipeline/`, never its sample invoices, output, `.env` or LLM client). It reads PDFs, scanned pages, e-invoices and zips of invoices; classifies the vendor; checks the arithmetic; self-corrects a critic pass; and writes a catalogue. Phase 7.6 ports it into **Bernie**, the first and, this phase, only shipped pack on the agent platform (ADR-0012): "a much better, agentic version" of the same pipeline, using durable jobs, asks, records, entities, skills and governance instead of a one-shot script.

Porting a notebook written for a trusted, offline, single-run context into a multi-tenant product that handles real financial documents raises questions the notebook never had to answer: what happens when a page is ambiguous (a notebook just guesses or fails); what a model may compute versus what code must; what happens to a bank account number; whether a near-match vendor is close enough; and what dependencies are acceptable in a shipped product versus a personal script.

## Decision
1. **Results stay inside Momentum** (D4): invoice records, task fields, the review screen, approval tasks, exports. No push to ERP/AP systems, and no contract matching — both are explicitly out of scope for Bernie and left as future packs.
2. **Money, dates and arithmetic are computed by code, never the model** (D9), continuing Phase 7.5's D6. `Money` is `Decimal`, serialised as strings in JSON, never float. The notebook's `reconcile.py` checks (total = subtotal + tax, line sums, due ≥ invoice date, …) port as deterministic code with **zero model calls**, run on every record, every time.
3. **No PyMuPDF (AGPL), no Tesseract (a system package), no Presidio/spaCy (too heavy), no new runtime dependency at all** (D10). Page splitting uses `pypdf` instead of PyMuPDF; page rendering reuses Phase 7.5's `momentum.files.render` (pypdfium2); scanned pages go to vision through the gateway instead of OCR (Phase 7.5 D4); redaction uses the SDK's regex-and-checksum scrubber (ADR-0012 §8.6) instead of Presidio.
4. **Bank details are never stored in full.** A payee bank is kept as `fingerprint` (HMAC-SHA256 with the workspace secret) and `last4` only — never a full account number or IBAN — and a changed fingerprint always routes to a person (D11), regardless of autonomy or auto-approval settings.
5. **Bernie never auto-approves by default** (D11). Auto-approval is a workspace setting, off unless an admin turns it on, and still bounded by the policy engine's rules (materiality, confidence floor, new vendor, anomalies) — turning the setting on does not bypass them.
6. **An e-invoice fast path with no model call.** A PDF/A-3 with an embedded Factur-X/ZUGFeRD/XRechnung XML, or an attached UBL 2.1 / CII D16B XML, is parsed deterministically (`defusedxml`) into the invoice model at confidence 1.0, skipping straight to the arithmetic checks. When the embedded XML and the visible page disagree on the total, that's a warning, not a silent pick of one.
7. **A bounded, evidence-only investigator for the hard cases.** The notebook's critic (one exact-mismatch, closed-root-cause call) is tried first; if a document still fails its checks, a tool-using investigator (≤ 8 steps, a page-text/table/find/look-at/sum/propose-fix toolset, its own budget) runs, but **every value it proposes must have been seen on the page** through one of its own tool calls — a value the tools never returned is rejected in code, not trusted from the model's say-so. If that still fails, Bernie asks a person, once, with evidence, rather than looping.
8. **Synthetic test data only** (carried from Phase 7.5 and CLAUDE.md): fictional vendors (Northwind Data, Acme Analytics, Contoso Markets, Fabrikam Feeds, Tailspin Research, Woodgrove Terminals), built at test time from YAML specs with `reportlab`. Real invoices never enter the repo; a private comparison against the notebook's own real-invoice output, and a private golden set, run only on the product owner's machine (`momentum packs compare`, `momentum packs golden export` — which refuses any `--out` inside the repo).

## Alternatives considered
| Option | Pros | Cons |
|---|---|---|
| Keep PyMuPDF for page splitting/rendering, as the notebook does | Less porting work, mature library | AGPL — incompatible with shipping Momentum as a product; rejected outright (D10) |
| OCR (Tesseract) for scanned pages, as the notebook does | Works offline, no gateway cost | A system package dependency the Docker image and every environment would need; vision through the already-integrated gateway (Phase 7.5 D4) covers the same need with no new dependency |
| Let the model compute totals/checks directly, as a notebook script might lean on it for speed | Simpler prompt, fewer steps | Exactly the failure mode D9 exists to prevent: a model can silently "fix" arithmetic instead of flagging it; checks must be reproducible and auditable |
| Store full bank account numbers/IBANs for easier display and matching | Simpler entity model | A real financial-data liability; fingerprint + last4 is enough to detect a change and show "which account" without ever holding the number |
| Auto-approve small invoices by default, to show value faster | Less clicking for pilot users | Rejected (D11): a shipped default that approves money movement without a person is not a default Momentum ships, whatever the invoice size |
| Let the investigator "recall" a value it's confident about without re-finding it on the page | Fewer tool calls, cheaper | Defeats the purpose of grounding; a hallucinated-but-plausible number is exactly the risk on a financial document |

## Consequences
- **Positive:** Bernie reuses Phase 7.5's file parsing, rendering, vision and reports engine entirely (D3) — nothing duplicated. The platform's effects/policy/ask machinery (ADR-0012) means Bernie's governance (who may approve what, when a person must be asked) is configuration and code review, not a one-off feature. The e-invoice fast path and the deterministic checks mean most invoices need no model call for the numbers that matter most.
- **Negative:** porting a notebook's OCR path to vision-through-gateway and its PyMuPDF splitting to `pypdf` is not a straight copy — both needed real rework (`docs/agents/porting-a-notebook.md` documents exactly what changed and why, as the worked example for future packs). The investigator's "must be found on the page" rule adds tool-call overhead on the hardest documents, which is the deliberate trade against grounding being optional.
- **Follow-ups:** `docs/agents/bernie.md` (users and admins); the "Accounts payable" dashboard role template (Phase 7.5's dashboards v2, extended per spec §6.6); `momentum seed --invoices` for demos and the UI audit.
- **Reversal:** removing or disabling the Bernie pack (`MOMENTUM_PACKS` without `bernie`, or turning the agent off) leaves the platform and every other pack untouched — Bernie is ordinary pack code with no special-cased platform behaviour. Auto-approval, once turned on, can be turned off per workspace at any time; records already approved stay as they are.
