# ADR-0010: Scale to ~150 people in one workspace

- **Status:** Accepted (product owner delegated Phase 7 review gates to the AI, 2026-10-04)
- **Date:** 2026-10-05
- **Deciders:** product owner (scope: ~150 people, many from Asana), AI (drafted, measured)
- **Amends:** ADR-0001 (its context assumed 10–15 users; the single-image decision stands)

## Context
Momentum was designed for 10–15 people. On 2026-10-01 the product owner set the target at **~150 people in one workspace**, with about 75 using it at the same moment. Phase 7 E7.1 load-tested a `momentum seed --scale` workspace (150 people, 8 teams, 60 projects, ~50,000 tasks with comments, dependencies, tags and followers) using `tools/load/locustfile.py` (2–8 s think time; Home, My Tasks, project lists, task details, inbox, search, edits, comments, new tasks, dashboards, workload).

Measured on the dev laptop (Docker Desktop, 14 cores shared by the app, Postgres and locust):
- One web process saturates at about **18 requests/s**. 75 active people make about 20/s, and 150 make about 38/s.
- Per-request costs were dominated by loading too much: whole task rows, descriptions included, for screens that show a title; ORM objects for 13,000 workload tasks; a 1.2 MB workload payload; per-level ancestor queries; and a `last_seen` write on every request.

## Decision
1. **Still one image (ADR-0001), with several web processes.** `MOMENTUM_WEB_WORKERS` (default 1) runs N uvicorn processes. For ~150 people use **4**. Realtime already fans out across processes through Postgres LISTEN/NOTIFY, and the job queue de-duplicates scheduled jobs, so the embedded worker in each process is safe. Split the worker out (`MOMENTUM_WORKER_MODE=separate`) only if job latency is measured to suffer. At 75 concurrent users every job succeeded and none were left waiting.
2. **Database connections are budgeted.** `workers × (pool + overflow + 2)` must stay under Postgres `max_connections`; the app warns at startup above 80%. For ~150 people: 4 × (5 + 5 + 2) = 48.
3. **Per-endpoint-class latency budgets** replace the single "reads < 150 ms" figure:

   | Class | Endpoints | p95 budget at 75 concurrent |
   |---|---|---|
   | Item reads | a task, its feed, sections, notifications, dashboards | < 150 ms |
   | List views | Home, My Tasks, a project's tasks, search, workload | < 400 ms (and the screen renders from cache while it refreshes) |
   | Writes | edit, comment, create | < 300 ms |
   | Realtime | a change reaching other open tabs | < 1 s |

   List views aggregate hundreds of rows per person (a heavy user has ~200 open tasks; a project ~800). They are cached on the client and refreshed in the background, so their p95 is a background cost, not a wait for a click.
4. **Per-person AI rate limit.** `MOMENTUM_AI_USER_CALLS_PER_HOUR` (default 200) caps one person's own successful model calls per rolling hour, so a stuck tab or a script can't use up the workspace budget. Agents have their own monthly budgets, sized for ~150 people (Pulse $40 / 12M tokens down to Planner $10 / 4M).
5. **Query rules for list endpoints** (performance.md "Scale rules"): select only the columns a screen shows, use plain rows rather than ORM objects for large lists, batch ancestor checks per level, filter in SQL rather than Python, and load payloads per row on demand (workload task lists).

## Alternatives considered
| Option | Pros | Cons |
|---|---|---|
| Keep one process and optimize until it fits | Simplest deploy | One Python process is CPU-bound near 18 req/s even with lean queries; there's no headroom for an agent burst |
| Separate API, worker and realtime services | Independent scaling | More infrastructure, auth and deploy steps; not needed at 150 people |
| A read cache (Redis) for Home / My Tasks | Faster list views | Another service plus invalidation for per-person, permission-filtered data; the measured costs were waste we could simply remove |

## Consequences
- Results at 75 concurrent on the dev laptop (5 min, 6,178 requests, 1 connection dropped by the Docker Desktop port proxy): aggregate p95 190 ms; item reads p95 60–79 ms; list views p95 190–370 ms (Home 300, My Tasks 240, a project 190, search 340, workload 370); writes p95 110–180 ms; realtime 400/400 deliveries at p95 193 ms. **Every class meets its budget.** Details: `performance.md` "Scale to ~150 people".
- The load test also found a realtime bug (events committed out of id order were skipped) and an unnecessary re-authorization of every connection on every task edit; both are fixed (register H39, H40).
- **The budgets are re-checked on Azure before go-live** (phase-8.md go-live checklist), using the same locustfile and `tools/load/realtime_probe.py` against staging. A laptop shared with Postgres and the load generator is not the production box.
- Undo: set `MOMENTUM_WEB_WORKERS=1` and `MOMENTUM_AI_USER_CALLS_PER_HOUR=0`. Nothing else depends on this ADR.
